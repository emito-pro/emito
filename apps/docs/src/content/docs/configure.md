This is where your notification types and templates live. Everything else in
Emito is generic; the `categories`/`events`/`channels`/`templateResolver`
passed into `createEmito({...})` in your generated `emito.config.ts` are the
part you actually write and maintain.

`emito init` already generated a starter `emito.config.ts` with one
category and one event, wired into a `createEmitoRuntime()` function. This
page explains the four pieces inside that `createEmito({...})` call, not a
separate file to create. A trimmed view of what's actually there:

```ts
// emito.config.ts, generated by `emito init`: this is the part you own
const emito = createEmito({
  database: { url: databaseUrl },
  redis: { url: redisUrl },
  redisClient: redis,
  repositories: { /* ...omitted... */ },

  // Starter category/event: edit or extend for your own notifications.
  categories: {
    general: {
      policy: 'opt_out',
      topics: {
        'welcome.sent': { channels: ['inApp'], description: 'Welcome notification' },
      },
    },
  },

  events: {
    'welcome.sent': {
      category: 'general',
      channels: ['inApp'],
      priority: 'low',
      description: 'Sent once, right after emito init, to prove delivery end-to-end',
    },
    // add more events here...
  },

  channels: {
    inApp: { providers: [/* ... */] },
    // email/sms added here if you selected them during `emito init`
  },
});
```

Once you're past the starter, extend the config to match your product.
Here's a more realistic example with multiple categories and a template
resolver:

```ts
const emito = createEmito({
  // ...database, redis, repositories as above...

  categories: {
    transactional: {
      policy: 'always',                         // can't be turned off
      topics: {
        'payout.settled': { description: 'Payout completed' },
      },
    },
    product: { policy: 'opt_out', topics: {} }, // on by default, user can disable
    marketing: { policy: 'opt_in', topics: {} }, // off by default
  },

  events: {
    'payout.settled': {
      category: 'transactional',
      channels: ['inApp', 'email'],
      priority: 'high',
      description: 'Sent once a payout has been settled',
    },
  },

  channels: {
    inApp: { providers: [/* ... */] },
    email: { providers: [/* ... */] },
  },

  // Optional: omit it and Emito passes payload straight through as `body`.
  templateResolver: {
    async resolve({ event, channel, lang, payload }) {
      if (event === 'payout.settled' && channel === 'inApp')
        return { subject: 'Payout completed', body: `We sent you ${payload.amount}.` };
      if (event === 'payout.settled' && channel === 'email')
        return { subject: 'Payout completed', html: `<p>We sent you ${payload.amount}.</p>`, text: `We sent you ${payload.amount}.` };
      return { body: '' };
    },
  },
});
```

## Categories

A category's `policy` controls whether subscribers can opt out:

- **`always`**: transactional, can't be turned off (e.g. security alerts).
- **`opt_out`**: on by default, the subscriber can disable it.
- **`opt_in`**: off by default (e.g. marketing).

Each category also has a **`topics`** map: one entry per event that
belongs to it, keyed by the event name, with an optional `description` and
an optional `channels` override (narrowing which channels *this specific
topic* can use, if different from the category's default). `emito init`
always generates this map even for a single starter event, because the
preference center (`/emito/v1/preferences`) reads topic labels from here, so
every event you add to `events` below should get a matching `topics` entry
in its category.

## Events

Each event maps to the category it belongs to, the channels it fans out
to, and a priority. This is your app's notification catalog: one entry
per distinct thing that can notify a user. Beyond the required
`category`/`channels`, an event can also set:

- **`description`**: short human-readable label (`emito init` always
  fills this in for its starter event).
- **`bypassPreferences`**: deliver regardless of the subscriber's
  preference toggle (rare; genuinely critical notices only).
- **`bypassRateLimit`**: skip the per-channel rate limiter for this event.
- **`digest`**: batch this event into a periodic digest instead of
  sending immediately (`{ windowMs, maxCount, channels? }`).

## Channels

`channels` wires actual provider instances to each channel name (`inApp`,
`email`, `sms`, `push`, `slack`, `telegram`, ...). See [Channels &
providers](/concepts/channels/) for the full list of what's available and
which package backs each one. `emito init` populates this with either a
real provider (if you supplied credentials) or `createMockProvider(...)`,
which logs to the console instead of sending; see [Backend](/backend/) for
the exact fallback pattern.

## Template resolver

Optional: omit it entirely and Emito passes the event payload straight
through as `body` with no rendering. When you do provide one, `resolve`
receives `{ event, channel, lang, locale?, timezone?, payload }`. `lang`
is required (the BCP-47 language to render in; see [Translate the
UI](/i18n/) for where it comes from), even if your resolver only supports
one language today. Return the content for that event+channel combination.
This is intentionally plain, since no template engine is imposed; reuse your
existing content builders or write the strings inline.

`payload` itself is required on every `send()` call, even for events with no
template variables — pass `{}` rather than omitting it. `send()` throws
`VALIDATION_ERROR` otherwise; see [Gotchas](/gotchas/).
